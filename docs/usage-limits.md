# AI利用量と費用の保護

2026-10-30確認。IP単位10回/分だけでは、異なるIPからの呼び出し総数に上限がない。
旧実装の maxRetries: 1 は、1回の評価につき最大2回のプロバイダー呼び出しを許す。
今回は maxRetries: 0 にし、すべての評価経路を事前予約で保護する。

## 制限の比較と初期値

| 仕組み | 初期値 | 役割 | 復旧 |
| --- | --- | --- | --- |
| IP単位 | 10回/分（既存） | 単一接続元の連打を抑制 | 既存のスライディングウィンドウ |
| 全体の日次上限 | 100回 | 1日の使い切り量を限定 | 翌UTC 00:00（日本時間09:00） |
| 全体の月次上限 | 2,000回 | 日をまたぐ継続消費を限定 | 翌月1日UTC 00:00 |
| 集中利用による一時停止 | 最初の予約から60秒間で20回を許可、次の要求で15分停止 | 複数IPの集中利用で枠が急減するのを抑制 | 900秒後 |
| 手動停止 | Redisのstopキー | 運用者が緊急停止 | キー削除またはTTL満了 |
| 金額による停止 | 未実装 | 単価変更、他用途のAPIキー利用も含めた支出制御 | プロバイダー側設定と併用を推奨 |

個人公開サービスの暫定値。1人5回なら20人/日、400人/月を目安に試せる。
利用実績がまだないため需要予測ではない。通常トラフィックを確認して調整する。
集中利用は攻撃の断定ではなく、正常な人気集中も止める。期間境界では前後の枠が連続利用できる。
日次・月次枠の拒否を優先し、その場合は集中利用による停止を追加しない。

## 実装と費用

Upstash RedisのLuaスクリプトで、停止確認・全上限確認・枠の予約を一つの不可分な処理にする。
同時アクセス・複数サーバーでも、許可された評価は上限以内になる。時刻はRedis TIMEを基準にする。
UTC月境界はアプリが計算し、Redis時刻と一致しない場合は安全側で503にする。
AI呼び出し前に計数し、タイムアウト、不正応答、接続失敗でも返却しない。失敗でも課金される可能性があるため。
Redis未設定・エラー・不正な上限設定では503。開発時の実API利用もRedis設定が必要。
全体上限・停止時は503とRetry-After、IP制限時は従来通り429。
既に予約済みの処理は停止後も完了できる。APIリトライは無効。

公式モデル資料ではJev 1.14/1.13とも入力100万トークン当たり$0.042、出力無料。
https://docs.typesafe.ai/models

| 仮定する1回あたり入力量 | 100回/日のAI費用 | 2,000回/月のAI費用 |
| --- | ---: | ---: |
| 1,000トークン | $0.0042 | $0.084 |
| 10,000トークン | $0.042 | $0.84 |
| 64,000トークン | $0.2688 | $5.376 |

実測ではなく試算。64kは現行の通常コンテキスト上限であり、請求金額の保証ではない。
Long contextは有効化しない。jev-latestの単価・仕様変更、税、為替、別経路の呼び出しは含まない。
厳密な金額予算は、実請求額の取得・料金変更への追随・他アプリの消費を扱う必要がある。
まず回数上限で確実に呼び出し量を抑える方を選び、TypeSafe側に支出上限があれば併用する。

Upstash公式料金はFreeが月500Kコマンド、従量課金が100Kコマンドあたり$0.20。
https://upstash.com/pricing/redis
追加の予約処理は1リクエストにつきEVAL 1回（内部Redis操作を含む）。実際の課金カウントは利用プランで確認する。
拒否された要求もRedisやVercelの実行・通信費を消費するため、これらの費用はAI回数制限だけでは上限にならない。
大規模な攻撃にはVercel等の入口での遮断、各サービスの予算通知・課金制限も必要。

## 運用

`.env.example`の4変数で上限を変更する。正の整数のみ有効。変更後は再デプロイする。
本番・プレビュー・開発で同じRedisを使うと同じ枠を消費する。分離したい場合は別DBを使う。
`jev-ranks:{usage}:`キーの接頭辞はデプロイで変えない。カウンターの削除、DB移行・データ消失は使用量をリセットする。
Redisの永続性と同一DBの継続使用が前提。単一の書き込み先を使い、地域ごとに独立したDBへ分散しない。
キーは固定数で、日付ごとの履歴は残さず、期間と回数だけ保存する。個人情報・本文は保存しない。

Upstashコンソールで以下を実行できる（認証済み管理者のみ）。

```redis
SET jev-ranks:{usage}:stop manual
# 解除
DEL jev-ranks:{usage}:stop
# 残り停止秒数、現在の予約数
TTL jev-ranks:{usage}:stop
HGETALL jev-ranks:{usage}:daily
HGETALL jev-ranks:{usage}:monthly
```

manual停止はTTLなしなら手動解除まで継続する。自動停止中も同じSETで恒久停止へ変更できる。
カウンターは利用者単位でなくサービス全体。予約済み・失敗分を含むため、請求実績とは一致しない。

## 検証

通常のVitestでは設定・障害・APIの拒否時にAIを呼ばないことを検証。
Redis実機のLua統合テストはredis-server/redis-cliをインストールし、以下で実行する。

```bash
RUN_REDIS_TESTS=1 pnpm test
```

テストはローカルの専用Redisプロセスを起動し、本番Redisや実AIを呼ばない。
